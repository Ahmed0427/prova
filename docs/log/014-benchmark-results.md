# 014: benchmark results (`docs/benchmarks.md`)

## 1. What and why

The phase 3 deliverable: a table of native vs revm cycles for a
compute-heavy contract and the ERC-20 (plus the phase 2 calls), split into
execution and setup/commit, with how to reproduce it and its caveats.
Generated by `./prova bench` (012) after the SHA-256 patch (013).

## 2. Decision

**What to put in the summary.** One row per kind of work: storage-bound
ERC-20 calls (a transfer, a transferFrom, a read, a revert), pure uint256
arithmetic (`fib`), memory (`sort`), division (`primes`), the keccak
precompile (`hashChain`) and a cross-contract call with a caught revert.
Both *execute* and *total* ratios, since the totals are dominated by costs
that have nothing to do with the execution model (commit).

**Which numbers.** Cycles, not wall time: deterministic and comparable; the
document says plainly that proving cost isn't exactly proportional and that
no proof was generated.

## 3. How it works

```
./prova bench tests/erc20.test && ./prova bench tests/compute.test && ./prova bench tests/calls.test
docs/benchmarks.md = summary (selected rows) + region split for one transfer
                     + the three generated tables + reproduce + caveats
```

## 5. Verification

Every summary number was checked against the generated tables
(`build/bench/{erc20,compute,calls}.md`); the "outside the regions" column
is total − setup − execute − commit. All three runs end with "native and
revm agree on every step". The claim about `udivmod256` was checked in
`stdlib/bigint.c` (shift-and-subtract, one iteration per quotient bit).
